CUSTOM ENDPOINT TROUBLESHOOTING

Which request
actually failed?

A 404 during model discovery and a 404 during generation need different investigations. Follow the operation before changing your prompt or retrying.

Separate discovery from generation

  1. Identify the operation. These examples call GET /v1/models before POST /v1/chat/completions. Record which one failed and its status.
  2. Check the constructed path. The SDK appends the operation to your base URL. Use the provider's documented API root, including its version segment where required. A complete chat endpoint is not an API root.
  3. Check the exact model and protocol. Listing a model for your key does not prove it supports Chat Completions. Check the provider's catalogue and current availability.
  4. Keep the request ID. The examples print the ID exposed by the SDK: requestID in JavaScript and request_id in Python. Never include the API key in a support report.

Some providers do not implement model listing. Confirm the endpoint contract before using a discovery gate; these examples deliberately require it.

Investigate the status in context

These are investigation starting points. The returned error and provider documentation determine the cause; a synthetic status cannot establish a live provider's error contract.

401 or 403: authentication and access

Check that the key belongs to the intended service, is current and has the required access. Confirm the intended environment variable is present without printing its value. In the fixtures, either status during discovery prevents any chat request.

402: credit or billing

Inspect the provider's returned message, account balance and applicable rates. The fixture checks that a failed completion prints the status and request ID, then exits without another completion attempt.

404: compare the failing paths

If discovery fails, check the host, API root, version segment and whether model listing is implemented. If discovery succeeds and chat fails, inspect the exact model ID, its supported protocol and current availability. A prompt edit cannot repair an unsupported endpoint.

429: inspect limits before retrying

Read the error and any Retry-After header, and check the provider's rate or concurrency limits. Both fixture clients set automatic retries to zero. A 429 carrying Retry-After still produces exactly one attempt at the failing operation.

503 or timeout: preserve the evidence

Check service status and retain the request ID if one was returned. Review usage before manually resending an interrupted billable request. The 503 fixture verifies the error path; timeouts and ambiguous completion outcomes are not tested here.

Run the same checks locally

Use Node.js 22+ and Python 3.9+. These commands use a POSIX shell; on Windows run the installation commands in PowerShell and use $env:PYTHON_BIN if you need a different Python executable.

git clone https://github.com/MacFinn/cheapclankers-examples.git
cd cheapclankers-examples
npm install
python -m pip install -r requirements.txt
npm test

The harness starts an ephemeral server on 127.0.0.1 and gives child processes fictitious credentials, a fixture model and that local endpoint. It does not load a .env file or buy inference. Inspect the verification harness and the Markdown test record before running it.

Use the result within its limits

This is a client behavior test against synthetic responses. It does not measure live model availability, production inference, streaming, tool calls, timeouts, concurrency or pricing. It is not a production retry strategy.
